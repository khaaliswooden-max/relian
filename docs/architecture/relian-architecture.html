System architecture

SealedPhase 0 · stop 01 · on or before 2026-08-16

The benchmark was sealed before the solution existed

RELIAN-BENCH's success criteria were committed and Ed25519-signed before any transform work was scored against them. That ordering is the whole point: a bar you can move after seeing the result is not a bar.

Version v1.2 seals 29 files under payload a8695c2c…, key fingerprint 233bb4406e2de606 — 7 COBOL programs, 425 held-out vectors and 89 public ones. The thresholds live in the ledger, not in a README: held-out BER ≥ 0.95, build rate 1.00, JaCoCo branch coverage ≥ 0.80.

The held-out vectors are not in this repository and are never read by an agent. They are scored in CI on main only — because a score returned on every push is a feedback channel, and a feedback channel is something you can fit against one commit at a time without ever intending to.

Stands on this

  • "Candidate X scored Y on criteria nobody could tune against"
  • Re-verification by a recipient, from the ledger alone

Does not stand on this

  • Any statement about COBOL outside the sealed corpus
  • Any claim the benchmark itself is representative of a customer estate
MeasuredPhase 0 · stop 02 · 2026-08-16 → 08-17

The deterministic transpiler clears its own bar

C1 is the pipeline's transform core and there is no model anywhere in that path. At the moment v1.2 was sealed, C1 was red on it: BER 0.7176, building 6/7 programs. That red is the receipt that the criteria came first.

WP-1.5.4 and WP-1.5.5 closed it. Measured in CI on PR #15 at commit 8c676e9: 425 / 425 held-out vectors match across all 7 programs, build rate 1.0000, JaCoCo branch coverage 0.8854 against a bar of 0.80.

Scope, stated rather than implied. The supported subset is COBOL-85: COMP-3 arithmetic, EVALUATE, PERFORM VARYING, OCCURS/SEARCH, INSPECT, edited pictures, VALUE, and CONTINUE/GOBACK/EXIT PROGRAM. Numeric business logic is emitted as BigDecimal with explicit COBOL rounding — ROUNDED is HALF_UP, an unrounded COMPUTE is DOWN.

Stands on this

  • Behavioral equivalence on the sealed corpus, held-out
  • Reproducibility — a second pass emits identical bytes

Does not stand on this

  • CICS, VSAM, JCL, embedded SQL, or copybooks in the transform path
  • IBM Enterprise COBOL — the oracle is GnuCOBOL 3.1.2.0
ShippedPhase 1 · stop 03 · 2026-08-16

The assessment engine — the first thing a customer can buy

WP-1.1 through WP-1.9 built src/assessment/: intake, LOC, cyclomatic complexity, construct coverage, risk tiering, report, CLI. It is read-only over customer source and fully offline — nothing in the package opens a socket or calls a model.

Determinism is asserted three ways, not assumed: two runs over the same tree produce byte-identical JSON and the same report_hash, and a CRLF copy of a tree scores identically to its LF original.

The capability list is not hand-maintained. The coverage analyzer reads SUPPORTED_STATEMENTS off the transpiler at call time and probes DATA DIVISION features by running real programs through it. Teach the transpiler a new verb and the report changes on the next run with nobody editing a list. Data features are reported three-state — supported, accepted but ignored, unsupported — because a clause that parses and is then discarded is not a clause you support, and conflating the two is how a migration silently loses semantics.

Stands on this

  • A priced, deliverable read-only assessment
  • Construct inventories on estates far outside the transpiler's subset

Does not stand on this

  • Any migration claim — assessment measures distance, not equivalence
  • Effort or cost forecasting; no such model exists
ShippedPhase 1 · stop 04 · 2026-08-16

Honest failure wired down to the statement

Before WP-1.2 there was no else branch in the transpiler's statement dispatch and no unsupported() anywhere. An unsupported verb that began a statement was silently discarded; one that followed a statement was absorbed into its predecessor and surfaced later as a misattributed error. Honest failure existed only at whole-program granularity, and only for two of the four observed failure shapes.

The if/elif chain became a dispatch table with an unsupported(verb, line_no) fall-through, so a refusal now names the verb and the line that carried it.

The refactor was gated on bytes, not on opinion. All five generated Java files regenerated SHA-256-identical before and after, and identical to the committed candidates. A behavior-preserving change that cannot be shown to preserve bytes is a change nobody should merge into a transform.

Stands on this

  • "Unsupported input produces a diagnosis, not output"
  • A demand signal ranked by real occurrence counts

Does not stand on this

  • Completeness of the diagnosis for constructs never exercised
ShippedPhase 2 · stop 05 · 2026-08-20

The limbs that produced numbers nobody measured were deleted

Three things left the tree in one phase, and their absence is now part of the architecture.

The risk-scoring limb (R1). It retrained a gradient-boosted model every twenty migrations on rows whose "cognitive complexity" feature was cyclomatic complexity × 1.2 — a fabricated input feeding a fabricated score, tightening on itself. Both the scorer and its pattern store were deleted. risk_score and test_coverage are now None by construction, not by configuration.

The generative-AI semantic analysis stage and the LLM test generator (R6). Both sent customer source code to a hosted model. They were deleted rather than flagged off, because a flag can be flipped and a deleted call cannot. semantic_score now has exactly one source: Stage 6 differential execution against the legacy oracle — which is the only measurement of semantic preservation this pipeline ever actually had. A model's self-reported confidence was never one.

Alongside that: the environment was pinned in requirements.lock, a toolchain guard added, and CI switched from "no failures" to asserting the exact test triple, so a test that quietly stops being collected turns the build red.

Stands on this

  • "No customer source reaches a generative model" — R6, structurally
  • Every emitted metric traces to a process that ran

Does not stand on this

  • Risk prioritisation of any kind — the capability is gone, not hidden
SealedPhase 2 · stop 06 · 2026-08-21

A second benchmark, sealed before the code it judges

R7 is bench-first: nothing is "supported" until a sealed benchmark covers it, and the bench commit must predate the merge. So the copybook work was gated on a benchmark that did not yet exist, and building it came first.

RELIAN-DISCOVERY-BENCH v0.1 — 15 copybooks, 124 elementary fields, 170 probe rows, 16 variants, 9 conditions and 6 gap rows — has its oracle layouts generated by GnuCOBOL 3.1.2.0 and was sealed under the same benchmark key on 2026-08-21. CI enforces the ledger on every run, and discovery-bench/ became frozen the moment the tag existed.

Stands on this

  • Layout claims measured against an oracle that predates the code

Does not stand on this

  • IBM Enterprise COBOL layout semantics — the oracle is GnuCOBOL
  • Copybook support inside the transform path; this is discovery only
MeasuredPhase 2 · stop 07 · 2026-08-21

Copybook resolver and static layout engine

src/discovery/copybook.py resolves the COPY fan-in graph and reports the missing-copybook table. layout.py computes static record layouts: offsets, lengths, SYNC padding, REDEFINES, OCCURS DEPENDING ON, RENAMES.

Round-trip against the sealed oracle: 186 / 186, tolerance zero. Not "within a byte" — identical.

Gaps compare by projection, not by label. A padding byte cannot be renamed into agreement with the oracle, which is the obvious way a layout engine passes a test it should fail. Two limitations are reported by the tool rather than absorbed by it, and None never silently becomes zero.

Stands on this

  • Record layouts a customer can check against their own DDL
  • A named, enumerated missing-copybook table

Does not stand on this

  • File inventory, lineage, or target-schema DDL — stop 09
MeasuredPhase 2 · stop 08 · 2026-08-22

The signed Data Discovery report

python3 -m src.discovery.cli report build emits a canonical report.json, a Markdown rendering that names the JSON as authoritative, a manifest of digests, and an Ed25519 instance signature over that manifest. If a signing key cannot be obtained it writes nothing — an unsigned artifact that looks signed is worse than no artifact at all.

Custody is split across two keys so that rotating or compromising one cannot put the other's claims in question. The benchmark seal key 233bb4406e2de606 signs ledgers and never a customer deliverable; the Visionblox release key 91e3a404155ba4dd countersigns reports and never a benchmark. The countersigning tool refuses the benchmark fingerprint outright.

Exactly one line crosses the customer perimeter: manifest hash, report id, instance fingerprint. Three digests, no content. Recipients check the result with verify_report.py --pin-fingerprint, which has four independently-failing layers and prints its own SHA-256 before it says anything else. The pin has no default, because without one a report re-signed under any key at all passes every internally-consistent check.

Stated because it is true and would be easy to leave out: no countersignature has ever been issued. Both dry runs read VALID AND UNATTESTED. The triple the CI gate asserts is 1100 passed, 10 skipped, 0 failed.

Stands on this

  • A verifiable discovery deliverable a recipient can check without trusting us
  • Perimeter compliance demonstrated by a leak test, not asserted

Does not stand on this

  • Any countersigned artifact — none exists
  • PDF rendering; Markdown is the one derived rendering
  • File inventory, lineage, target-schema DDL
We are hereMeasuredPhase 3 · stop 09 · WP-2.4 / 2.4a · 2026-08-22

File inventory, lineage, and target-schema DDL

Four modules that did not exist before: jcl.py reads //name DD, DSN=, DCB= sub-parameters, DISP=, in-stream data and EXEC PGM=; files.py joins SELECT, FD and OPEN into one inventory and cross-checks record length against the JCL's LRECL; lineage.py derives program→dataset edges from OPEN modes and publishes the bound on its own coverage; ddl.py emits PostgreSQL DDL against a published mapping table. A load-and-reconcile gate runs the generated DDL against a real postgres:16 in CI, because DDL nobody has executed is DDL nobody should ship.

The cross-check on AWS CardDemo: 13 datasets where the FD record length and the JCL LRECL agree exactly, 0 that disagree, 41 where the JCL declares no LRECL to check against, and 194 with no resolvable layout. Four of the agreements arrive through COPY, which means the resolver, the layout engine and the JCL parser — three independent pieces of machinery — all had to be right for the delta to be zero.

The most useful thing in the work package is a defect it found in itself. NO_LAYOUT was first reported as one number, 204. Broken down by cause, the breakdown immediately showed the dry run had called the inventory without the copybook resolver, so every FD whose record arrives through COPY was miscounted. Ten rows moved. The superseded figures are kept and accounted for rather than deleted — a count that changes without a dated reason is a count nobody can audit.

A second defect was planted rather than found: the naive per-line DCB=(…) scan is kept in the test file permanently and asserted to fail on a continuation that splits across records. It returns a plausible, complete-looking, wrong answer — the fields it drops are silently indistinguishable from a DD that never declared them, and the one field that survives is exactly the one the cross-check turns on.

Not built, and not implied: the data-dictionary rendering. Three of the four surfaces this stop was defined by shipped; that one did not, and there is no module for it.

Stands on this

  • A file inventory and lineage a customer can check against their own JCL
  • Target-schema DDL that has been executed against a real database, not just generated

Does not stand on this

  • Dictionary rendering — no module exists
  • Lineage beyond OPEN-mode edges; the coverage bound is published with the result

The countersignature flow is proven end to end — but only under a stand-in key generated inside a test. Nothing in this repository has ever held the release key, and nothing ever will: custody is the operator's, and R4 keeps private material out of the repo, out of CI, and out of any agent session.

Not builtPhase 4 · stop 11

Corpus v2 and the scope extension it gates

"Migrates COBOL" is licensed today only for the subset the sealed corpus exercises. Extending it is a benchmark action before it is a grammar action: corpus v2 harvests third-party COBOL, seals it, and only then may CICS, VSAM, JCL, embedded SQL or copybooks-in-transform be attempted. Each construct pair earns the word "supported" by clearing held-out CI, and the bench commit must predate the grammar merge.

The distance is already measured, and it is large. Across three real-world corpora the assessment engine found 2,190 unsupported occurrences, and six constructs account for roughly 70% of everything blocking migration: EXIT (368), EXEC (306), CONTINUE (271), WRITE (224), GO TO (186), CALL (183). The cheapest third of that backlog is dispatch-table work with no new semantics.

Construct coverage on those corpora — AWS CardDemo 0.8511, the OMP course corpus 0.6945, GnuCOBOL's own tests 0.5968 — is graded PLAUSIBLE, not VERIFIED, for a specific reason: not one third-party program parsed cleanly under the then-bundled grammar, so all three were analysed through the token-scan fallback. The grammar was replaced at WP-2.0 and these figures have not been re-measured since.

Blocking

  • Corpus v2 not harvested, not sealed
  • Dry runs need re-measuring against the replaced grammar
  • Third-party licensing must be cleared per source
Not builtPhase 4 · stop 12

Attestation that is not simulated

Today's attestation self-identifies as simulated: true, and the pipeline refuses to issue even that over unmeasured values — if Stage 6 did not measure, Stage 7 is skipped outright. The reasoning is worth keeping: signing a fabricated number does not make it true, it makes it tamper-evident, which is strictly worse because it lends the number a guarantee it has not earned.

Retiring the flag needs a real integration; nothing simulated ships (R5), so the flag stays until the integration is real. Symbolic test generation returns empty by construction and stays that way until KLEE is genuinely wired in. The risk model was deleted, not trained — any re-entry starts from zero and is bench-gated like everything else.

Blocking

  • No attestation backend selected or integrated
  • KLEE not integrated; generated-test count is 0 by construction

The five rules this page obeys

  • R1 — a metric is measured or None. Never a constant or a default wearing a measurement's name.
  • R2 — honest failure is a feature. Unsupported input gets a diagnosis, never a silent pass.
  • R5 — nothing simulated ships; where an integration is absent it is said plainly.
  • R7 — bench-first. No construct is "supported" until a sealed benchmark covers it and CI passes.
  • R9 — every externally visible number carries a grade and a basis. See the appendix.

What is safe to say in a room

That Relian assesses a COBOL estate offline and read-only, and produces a signed, independently verifiable discovery report. That its transpiler clears a benchmark sealed before the transpiler was written, on vectors it has never seen. That it refuses rather than approximates.

What is not

That anything has been migrated for a customer. That any report has been countersigned. That the tool handles CICS, VSAM, JCL, embedded SQL, copybooks in the transform path, or IBM Enterprise COBOL semantics. That attestation is real — it self-identifies as simulated, and the pipeline skips it whenever validation was not measured.

The second tab of relian-architecture.html. This file is the readable source; the Atlas renders it as its Technical Summary tab.

Status: pre-MVP research prototype. Not production. Zero completed customer migrations. Zero countersigned reports issued. Every figure in this document was produced by a process that ran and is traceable to a file in this repository; anything not measured is written as None or "not measured", never as a default (R1). 1. What Relian is

Relian is a legacy refactoring substrate: a toolchain that assesses a COBOL estate, resolves and lays out its data structures, deterministically transpiles the subset it genuinely supports to Java, and proves the result by executing the original and the migration against each other — then signs the outcome so a recipient can check it without trusting Visionblox.

Two properties define the product, and everything else in the architecture is in service of one of them:

  1. The customer's source code never leaves the customer's machine. The CLI is offline and read-only over the codebase. Exactly one line crosses the perimeter, and it carries three digests and no content.
  2. Every quality number is a measurement or it is absent. There are no constants, defaults, or formulas standing in for observations, and the pipeline refuses to attest anything it did not measure.

The commercial consequence of (2) is unusual and worth stating up front: Relian will return "we could not migrate this" for programs a less careful tool would hand back as finished Java. That refusal is the thing being sold.

2.2 What crosses the perimeter

One line, produced by report countersign-request: manifest hash, report id, instance fingerprint. No source, no field names, no record contents, no file paths. The constraint is enforced by a leak test, not by convention.

2.3 Operator side (R4)

tools/countersign.py runs only in the operator's custody. The Visionblox release key is read from disk and its passphrase is taken via getpass at the moment it is needed — never from argv (world-readable in /proc, and it lands in shell history), never from the environment (inherited by every child, dumped by crash reporters), and never printed. Two of those three guards are AST walks over the tool, not greps, and each asserts that it found something to walk.

Two keys, two claim classes. The benchmark seal key 233bb4406e2de606 signs ledgers and never a customer deliverable. The Visionblox release key 91e3a404155ba4dd countersigns reports and never a benchmark. The countersigning tool refuses the benchmark fingerprint outright. If either key is rotated or compromised, the event does not put the other's claims in question — which a single key could not give you.

2.4 Recipient side

tools/verify_report.py --pin-fingerprint <fp>. Four layers, each failing independently: files against the manifest, the manifest hash, the instance signature, the countersignature. The pin is required and has no default, because without one a report re-signed under any key at all passes every internally-consistent check — the files match the manifest, the manifest recomputes, and the signature verifies under the key the forger generated. The pin is the only layer that sees it. The tool prints its own SHA-256 before it says anything else, and that digest is pinned by the test suite.

2.5 Verification substrate (CI only, R3)

Two sealed, Ed25519-signed benchmarks whose ledgers CI verifies on every run:

  • RELIAN-BENCH v1.2 — 7 COBOL programs, 425 held-out and 89 public vectors, 29 files under payload a8695c2c…. Thresholds live in the ledger: held-out BER ≥ 0.95, build rate 1.00, JaCoCo branch coverage ≥ 0.80.
  • RELIAN-DISCOVERY-BENCH v0.1 — 15 copybooks, 124 elementary fields, 170 probe rows, oracle layouts generated by GnuCOBOL 3.1.2.0.

Held-out vectors are not in this repository and are never read by an agent. They are scored on main only. The reason is not runner minutes: a score returned on every push is a feedback channel, and a feedback channel is something you can fit against one commit at a time without ever intending to. Nudge a rounding mode, push, read the BER; nudge it back, push, read it again. Nobody has to see a single held-out vector for the held-out set to stop measuring generalisation.

3. The production cycle

Seven stations. Three of them can end the run with no output.

#StationCan it stop the run?
01Intake — file discovery, encoding, line endingsno
02Assess — LOC, complexity, construct coverage, risk tierno
03Discover — COPY fan-in, record layouts, gapssigns or writes nothing
04Transpile — dispatch table → Java; second pass must hash-match the firstyes — out of subset
05Validate — javac + cobc, then every input through both binariesyes — oracle unavailable
06Gate — BER ≥ 0.95, build = 1.00, branch ≥ 0.80, all measuredyes — threshold missed
07Deliver — signed, countersigned, recipient-verified—

Behavioral equivalence requires **byte-identical stdout and the same process exit code**. A clean build is not evidence of equivalence and is never treated as such.

The honest-failure rail. An out-of-subset construct produces a refusal that names the verb and the line; no Java is written, not even a commented placeholder. If the oracle cannot be executed, equivalence is reported as not measured rather than assumed. If a threshold is missed, no attestation is issued — signing a fabricated number does not make it true, it makes it tamper-evident, which is worse, because it lends the number a guarantee it has not earned.

The shipped demo exercises this deliberately: two of its programs are expected to fail, and one of them is 93% transpilable. It still gets a diagnosed refusal and emits no Java, because 93% is not 100% and a partial migration that looks whole is the failure mode with a real cost.

4. Where the build stands

Twelve stops across four phases. The Build Atlas carries a movable flag; the position of record is the data-current attribute on #rail in that file.

Phase 0 — substrate · complete

  1. Bench sealed first. RELIAN-BENCH's criteria were committed and signed before any transform work was scored against them. At v1.2's sealing, C1 was red on it (BER 0.7176, build 6/7) — which is the receipt that the ordering was real.
  2. C1 clears the bar. 425 / 425 held-out vectors, build 1.0000, branch coverage 0.8854, measured in CI on PR #15 at 8c676e9.

Phase 1 — assessment · complete (2026-08-16/17)

  1. Assessment engine. WP-1.1 → WP-1.9. Read-only, offline, deterministic: two runs over the same tree produce byte-identical JSON and the same report_hash, and a CRLF copy scores identically to its LF original. The capability list is not hand-maintained — the analyzer reads SUPPORTED_STATEMENTS off the transpiler at call time and probes DATA DIVISION features by running programs through it. Features are reported three-state (supported / accepted but ignored / unsupported), because a clause that parses and is then discarded is not a clause you support.
  2. Honest failure wired. Before WP-1.2 there was no else in the statement dispatch and no unsupported() anywhere: an unsupported verb that began a statement was silently discarded, and one that followed a statement was absorbed into its predecessor and surfaced as a misattributed error. The dispatch-table refactor was gated on bytes — all five generated Java files regenerated SHA-256-identical.

Phase 2 — discovery · complete (2026-08-20/21)

  1. Fabricated limbs removed, environment pinned, CI switched to asserting the exact test triple rather than "no failures".
  2. RELIAN-DISCOVERY-BENCH v0.1 built and sealed — before the code it judges (R7).
  3. Copybook resolver + layout engine — 186 / 186 against the sealed oracle, tolerance zero. Gaps compare by projection rather than by label, so a padding byte cannot be renamed into agreement.
  4. The signed Data Discovery report. Canonical report.json, a Markdown rendering that names the JSON as authoritative, a manifest, and an Ed25519 instance signature. If a key cannot be obtained the command writes nothing. The triple the CI gate asserts is 1100 passed, 10 skipped, 0 failed.

Phase 3 — delivery · current position (2026-08-22)

  1. File inventory, lineage, and target-schema DDL ← we are here. Four new modules: jcl.py (DD statements, DCB= sub-parameters, continuations), files.py (the SELECT/FD/OPEN join and the LRECL cross-check), lineage.py (OPEN-mode program→dataset edges with their coverage bound stated), and ddl.py (PostgreSQL DDL, executed against a real postgres:16 in CI rather than merely generated). On AWS CardDemo: 13 datasets where FD record length and JCL LRECL agree exactly, 0 disagreements, 41 with no LRECL declared and 194 with no resolvable layout. Breaking NO_LAYOUT down by cause immediately exposed a defect in the dry run itself — it had run without the copybook resolver — and the superseded figures are kept and accounted for rather than deleted. The dictionary rendering did not ship and no module for it exists. The demo carries stops 5–9 as of 2026-08-23. Until then demo/ imported nothing from src/discovery/ and had not been touched since WP-1.x, so the walkthrough showed a Phase 1 product while the build stood here. python3 -m demo --discovery-only now runs the resolver, layout engine, file inventory, lineage graph, DDL generator and signed-report surface over a committed synthetic tree, and cross-checks its own layouts against the sealed oracle: 22 / 22 offset-and-length comparisons, tolerance zero, seal verified across all three layers before a row is read.
  2. First countersigned report. The flow is proven only under a stand-in key generated inside a test. Two things gate it: visionblox-release-key-v1.pub — public material, the one artifact still missing — reaching the repository so the published fingerprint can be checked against the actual key rather than a transcription of it; and one real engagement. Until then every report is VALID AND UNATTESTED, which is the correct label, not a caveat.

Phase 4 — scope · not built

  1. Corpus v2 and scope extension. Extending "migrates COBOL" is a benchmark action before it is a grammar action (R7): harvest third-party COBOL, seal it, and only then attempt CICS, VSAM, JCL, embedded SQL, or copybooks-in-transform. The bench commit must predate the grammar merge.
  2. Attestation that is not simulated, plus KLEE symbolic test generation. Nothing simulated ships (R5), so the simulated: true flag stays until the integration is real. The risk model was deleted, not trained; any re-entry starts from zero.

5. Scope — what is and is not supported today

Supported (the COBOL-85 subset the sealed corpus exercises): COMP-3 arithmetic, EVALUATE, PERFORM VARYING, OCCURS/SEARCH, INSPECT, edited pictures, VALUE, CONTINUE / GOBACK / EXIT PROGRAM. Numeric business logic is emitted as BigDecimal with explicit COBOL rounding semantics — ROUNDED is HALF_UP, an unrounded COMPUTE is DOWN.

Not supported, and not claimed: CICS, VSAM, JCL, embedded SQL, copybooks inside the transform path, and IBM Enterprise COBOL semantics (the oracle is GnuCOBOL 3.1.2.0).

The distance to a real estate is measured and large. Across three third-party corpora the assessment engine found 2,190 unsupported occurrences, and six constructs are roughly 70% of everything blocking migration:

6. Known limitations and open risks

  • No countersignature has ever been issued. Both dry runs read VALID AND UNATTESTED.
  • No customer engagement has been run, so there is no measured engagement duration, cost, or effort figure anywhere — and inventing one would be an R1 violation.
  • The public release key is not in the repository. Until it is, the published fingerprint is re-derivable in principle but not checked against the actual key inside the suite. This is the single smallest open item with the largest credibility effect.
  • Third-party construct-coverage figures are graded PLAUSIBLE, not VERIFIED. Not one third-party program parsed cleanly under the then-bundled grammar, so all three corpora were analysed through the token_scan fallback. The grammar was replaced at WP-2.0 and these figures have not been re-measured since — re-running the dry runs is cheap and would either confirm or correct them.
  • README.md capability table — corrected 2026-08-22. Four rows had gone stale against the WP-2.0.-2 / WP-2.0.-3 removals: "LLM semantic analysis — working when API keys present" (the stage was deleted under R6), test generation and risk scoring (both described as pending integration or training when the code paths were deleted), and the orchestrator's stage count. All four now state the removals, and the risk row names the product that does exist — src/assessment/risk.py, graded PLAUSIBLE as a policy.
  • The demo's discovery tree is synthetic. examples/demo is hand-written demonstration code. Its inventory and lineage figures describe that tree and nothing else; no customer estate has been discovered, so there is no measured figure for what discovery finds in one.
  • The transpiler's oracle is GnuCOBOL 3.1.2.0, so equivalence is equivalence against GnuCOBOL. Any claim about mainframe behaviour requires an IBM oracle that does not exist here.

8. Using the Build Atlas

relian-architecture.html is one self-contained file. No build step, no sibling files, no external assets but Google Fonts. Open it from disk, email it, or project it; it is also what https://khaaliswooden-max.github.io/relian/ serves.

The two tabs. Build Atlas is the three-plate visual brief; Technical Summary is this document. Both panels are real HTML inside the one file, so the summary is present with JavaScript disabled and when the page is printed — it is switched, not fetched.

Moving the position flag. Click any stop on Plate III and the flag plants there, the stops behind it fill in, the phase bands advance, and the record panel swaps to that stop's state. Arrow keys work too; the controls under the panel step forward and back.

That is a view change. The position of record is the data-current attribute on #rail in the file — edit it and commit, and the build's position becomes a version-controlled fact rather than browser state.

As the build advances, a newly completed stop needs three edits in relian-architecture.html: its data-state on the rail, its panel copy and status chip, and any row it touches in the provenance appendix. A stop does not move from not built to measured until a command has been run and its output recorded — the same rule as everywhere else.
