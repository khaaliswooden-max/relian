# RELIAN-DISCOVERY-BENCH v0.1 — specification

**Status:** authored, **not sealed**. The tag `relian-discovery-bench-v0.1`
does not exist yet, and until it does `discovery-bench/` is authorable under
`CLAUDE.md` rule 4 as amended at `fcdef19`. After the tag it is frozen
identically to `bench/`.

**What this benchmark is.** A layout oracle: fifteen COBOL copybooks and, for
every named field in them, the byte offset and length GnuCOBOL 3.1.2.0 actually
gives it. It is the answer key that WP-2.2's `discovery.copybook` resolver will
be graded against, and it exists before the resolver does (R7).

**What makes it re-derivable.** There is no held-out split, because there is
nothing to withhold: the ground truth *is* the answer key, and the whole claim
is that a third party can reproduce it. `oracle/oracle.json` is generated by
`cobc` and committed; CI regenerates it on a clean runner and diffs
byte-for-byte. Every file the seal covers is present in the public repository,
so `expected_absent` is empty and must stay empty.

## 3. The corpus

### 3.1 Seeded (3)

`MUBBREC.cpy`, `MUBCONS.cpy` and `MUBCUST.cpy` are **byte-identical copies** of
`examples/demo/copy/*.cpy`. Two copies of the same bytes exist, one
agent-editable and one frozen, and
`tests/test_bench_oracle.py::test_seed_copies_are_byte_identical_in_both_directions`
asserts identity in both directions so divergence goes red rather than silent.
If the demo copybooks ever need to change, the discovery bench re-versions —
that is the intended forcing function (D10).

They are not decoration. `MUBBREC.cpy` supplies three `FILLER` items, which are
half of the corpus's gap rows, and `BPR-AMOUNT-DUE PIC ZZZZZZZZ9.99`, which is
the field that exposed the probe defect in §5.

### 3.2 Authored (12), one axis each

Minimal by design, so that a WP-2.2 round-trip failure names its own cause.
Each file carries an in-band header stating its axis and that it is synthetic,
authored for this benchmark, and not derived from any customer or benchmark
source. They are authored rather than lifted, but `examples/demo/src/MUBPOST.cbl`
was read first — its inline `REDEFINES WS-POST-DATE` and
`OCCURS 1 TO 24 DEPENDING ON CM-HIST-COUNT` are constructs that already compile
here, and D07 and D08 are anchored to those shapes.

| File | Axis | Notes |
|---|---|---|
| `D01_display.cpy` | DISPLAY numeric | signed/unsigned, `V` implied decimal, leading (`SPPP9(04)`) and trailing (`S9(04)PPP`) scaling positions, 1- and 18-digit ends |
| `D02_binary.cpy` | COMP / COMP-4 / BINARY / COMP-5 | 1-, 2-, 4-, 8-digit boundaries of the `1-2-4-8` rule, plus COMP-5 at two widths |
| `D03_packed.cpy` | COMP-3 | consecutive digit counts 1–8, where `ceil((d+1)/2)` is visible; unsigned and `V`-scaled hosts |
| `D04_sign.cpy` | SIGN clause | LEADING/TRAILING SEPARATE (5 bytes) against both embedded forms (4 bytes), with default `S9(n)` as control |
| `D05_occurs.cpy` | OCCURS fixed | on an elementary item and on a group item, each bracketed by scalars |
| `D06_occurs_nested.cpy` | OCCURS nested two deep | INDEXED BY at both levels; inner stride ≠ outer stride |
| `D07_odo.cpy` | OCCURS DEPENDING ON | probed at min (1) and max (4); both lengths recorded |
| `D08_redefines.cpy` | REDEFINES | equal-length, smaller, and of a group — two redefinitions of one target |
| `D09_conditions.cpy` | level-88 | single, multi-VALUE, `VALUE … THRU`, and one on a COMP-3 host |
| `D10_sync.cpy` | SYNCHRONIZED | 20 declared bytes in a 25-byte group; the 5 slack bytes are the axis |
| `D11_renames.cpy` | level-66 RENAMES | plain RENAMES, `RENAMES … THRU`, and a THRU ending on a group |
| `D12_edited.cpy` | edited / JUSTIFIED | BLANK WHEN ZERO on two host kinds, `B` and `/` insertion, floating currency with `CR`, JUSTIFIED RIGHT on `X` and `A` |

One authoring constraint was discovered rather than assumed. GnuCOBOL rejects
any item declared *after* an ODO table in the same group:

```
error: 'D07-ENTRY' cannot have OCCURS DEPENDING because of 'D07-TRAILER'
```

so `D07_odo.cpy` puts its table last. That is the standard's rule, enforced;
the copybook was fixed before sealing, which is where a copybook defect belongs
(§4 escalation triggers).

## 4. How the oracle is measured

### 4.1 The routes run in a fixed order, and the order is a contract

**Route A** — `cobc -x -t <lst> -ftsymbols -I<corpus> <driver>` over a driver
that does nothing but `COPY` the copybook into WORKING-STORAGE. Yields per-field
SIZE, the declaration structure, and **the group total**.

**Route B** — the generated probe. It cannot be emitted at all until Route A has
produced the group total, because that total is what sizes the redefining byte
table it scans.

Route A is not a convenience. It is the independent second opinion that makes
Route B checkable: the probe measures offsets, the listing states sizes, and
every field must agree on length to the byte with zero tolerance. Both come
from `cobc`, so an error in the harness cannot make the two agree with each
other while both are wrong.

### 4.2 What the probe does

1. `MOVE LOW-VALUES` to the whole group (or to the redefining byte table).
2. `MOVE HIGH-VALUES` into exactly one field.
3. Scan the group byte by byte; report the first `FF`, the last `FF`, and how
   many `FF` bytes there were.

The first `FF` is the field's **1-based** offset. The extent `last − first + 1`
is its length. The count is carried separately and asserted equal to the extent:
if a field's bytes were ever not contiguous, that is a finding about the
compiler, not a number to average away.

Offsets are 1-based because that is what §0.5 measured — `WS-CW-ACCOUNT` = 1,
`WS-CW-NAME` = 11 — and converting at the boundary is a place to be wrong (D8).
`FUNCTION HEX-OF` does not exist in GnuCOBOL 3.1.2 (T12) and is never emitted.

### 4.3 Two byte-window strategies, and why there are two

The form WP-2.1 specifies — an `01` item that `REDEFINES` the group as
`OCCURS <total_len> TIMES PIC X(01)` — is used for fourteen of fifteen
copybooks. It cannot be used on `D07_odo.cpy`, measured:

```
error: the original definition 'D07-ODO' cannot be variable length
```

A group carrying OCCURS DEPENDING ON cannot be redefined at all, so that
copybook reads bytes through reference modification on the group itself,
`D07-ODO (I:1)`, which needs no redefinition. The two strategies are proved
equivalent rather than assumed equivalent:
`test_both_byte_windows_agree_on_a_fixed_copybook` probes a fixed-length
copybook under both and asserts every row is identical.

Probes are compiled with `-debug`, so an out-of-range subscript aborts loudly
instead of reading whatever is next in memory. A probe that silently read past
its group would produce plausible numbers.

## 5. Why the probe reference-modifies, and what that corrects

WP-2.1 §3.3 specifies `MOVE HIGH-VALUES TO <field>`. **That form is unsound for
one of the twelve axes**, and it fails silently rather than loudly. Measured on
GnuCOBOL 3.1.2.0:

| Receiving item | `MOVE HIGH-VALUES TO <field>` | `MOVE HIGH-VALUES TO <field> (1:)` |
|---|---|---|
| `PIC ZZZZZZZZ9.99` (numeric-edited) | first 0, last 0, **count 0** | first 1, last 12, count 12 |
| `PIC ZZZ9 BLANK WHEN ZERO` | first 0, last 0, **count 0** | first 24, last 27, count 4 |
| `PIC XXBXX` (alphanumeric-edited) | first 13, last 17, **count 4** | first 13, last 17, count 5 |
| `PIC X(06) JUSTIFIED RIGHT` | first 18, last 23, count 6 | first 18, last 23, count 6 |
| `PIC S9(09)V99 COMP-3` | first 11, last 16, count 6 | first 11, last 16, count 6 |

The plain move to a numeric-edited item compiles, runs, exits zero, and writes
**no high-value bytes at all** — the figurative constant is moved as a numeric
value and edits away to spaces. A probe built on it would have recorded
`offset: 0, length: 0` for every numeric-edited field in `D12_edited.cpy` **and
for `BPR-AMOUNT-DUE` in the seeded `MUBBREC.cpy`**, whose true layout is offset
46, length 12. Under D8/R1 a zero is not an honest answer, and a fabricated zero
that looks like a measurement is worse than a null.

The alphanumeric-edited row is the subtler half of the same defect: the extent
is right but the count is 4 of 5, because the `B` insertion position stays a
space. The contiguity assertion would have raised on it — correctly — and the
extent would still have been usable. The numeric-edited case has no such
tell-tale.

`(1:)` reference-modifies the item, which makes the receiving field
alphanumeric of the item's full length regardless of its category, and fills
every byte. Measured across all fifteen copybooks it is exact for DISPLAY,
COMP, COMP-3, COMP-5, numeric-edited, alphanumeric-edited, JUSTIFIED, BLANK
WHEN ZERO, group items, REDEFINES aliases and level-66 RENAMES aliases alike.

**Consequence for T13, recorded rather than quietly dropped.** `-Warchaic`
fires on `MOVE <figurative constant> TO <numeric item>` and does *not* fire on
the reference-modified form, because reference modification makes the receiving
item alphanumeric. Two related measurements:

* `-Warchaic` is **not enabled by default** in GnuCOBOL 3.1.2. A default
  compile of the plain form reports `0 warnings in compilation group`; the
  warning appears only when the flag is passed.
* The harness passes neither `-Warchaic` nor `-Werror`, does not suppress
  warnings globally, and does not treat any warning as failure. Warnings are
  carried through and reported.

## 6. The tiling invariant is conditioned, or it is wrong (D9)

"Fields tile the group with no gap or overlap" holds for `MUBCUST.cpy` because
it is flat. It fails **by design** under REDEFINES (deliberate overlap),
level-66 RENAMES (deliberate aliasing), OCCURS DEPENDING ON (variable extent)
and level-88 (no extent) — which is most of what this corpus exists to test. A
gate that fires on correct behaviour trains its readers to wave it through.

What is asserted instead, per copybook and independently per ODO variant:

> Over the projection of **named, elementary, non-redefining, non-renaming**
> fields, the union of `[offset, offset+length)` plus `gap`-sourced spans covers
> `[1, group_length]` **exactly once**.

Aliases are asserted separately:

* a **REDEFINES** field lies wholly within the extent of what it redefines;
* a **level-66 RENAMES** does *not* — `RENAMES A THRU B` is deliberately longer
  than `A` — so it is asserted to start at what it renames and to stay inside
  the record.

## 7. `gap` rows are derived, not measured, and are kept apart

`FILLER` cannot be the receiving item of a `MOVE`, and neither can the slack
bytes `SYNCHRONIZED` inserts. Both are real bytes and neither is measurable by
the probe: they are recoverable only as the bytes no named field claims.

So they are computed by subtraction, carried in their own `gaps` array with
`"source": "gap"`, and **never placed in `fields`**. A derived span does not sit
in the same list as a measurement (D8), and no field row is ever given a
fabricated zero.

All six gap rows in this corpus:

| Copybook | Offset | Length | Cause |
|---|---|---|---|
| `D10_sync.cpy` | 2 | 3 | SYNC slack before `D10-BIN-A` (4-byte COMP) |
| `D10_sync.cpy` | 10 | 1 | SYNC slack before `D10-BIN-B` (2-byte COMP) |
| `D10_sync.cpy` | 16 | 1 | SYNC slack before `D10-BIN-C` (8-byte COMP) |
| `MUBBREC.cpy` | 11 | 2 | `FILLER PIC X(02) VALUE SPACES` |
| `MUBBREC.cpy` | 44 | 2 | `FILLER PIC X(02) VALUE SPACES` |
| `MUBBREC.cpy` | 58 | 2 | `FILLER PIC X(02) VALUE SPACES` |

Level-88 condition names have no storage at all. They carry
`offset: null, length: null` in a `conditions` array and appear in **no** field
row, because a zero is not an honest answer for a thing with no extent (R1).

Every object in `oracle.json` that holds a number carries a `source` from
`{probe, listing, gap, derived, design-constant}`. The rule has no exceptions,
and `oracle_layouts.lint()` enforces it over the whole document — an exception
list is where an unsourced number eventually hides (gate ④).

## 8. Where GnuCOBOL 3.1.2 diverges, or is simply lossy

Measured behaviour of this compiler, recorded rather than "fixed". IBM
Enterprise COBOL may differ on any of these; that difference is **unmeasured**
(◐) and is a real limitation of a GnuCOBOL-derived oracle, which belongs in the
customer report as well as here.

1. **`SYNCHRONIZED` does align.** `default.conf` carries
   `synchronized-clause: ok` and the compiler inserts slack: `D10_sync.cpy`
   declares 20 bytes of fields and occupies 25. Alignment is to the item's own
   width (2/4/8), which matches the usual mainframe rule, but the *amount* of
   slack depends on `binary-size: 1-2-4-8` and would move under a different
   dialect setting.
2. **`COMP-4` and `BINARY` are normalised to `COMP` in the listing.**
   `D02_binary.cpy` declares all three; Route A shows `COMP` for each. The
   distinction survives only in the sealed copybook, not in the oracle's
   `listing.picture`.
3. **The `SIGN`, `JUSTIFIED` and `BLANK WHEN ZERO` clauses are erased from the
   listing's PICTURE column.** `PIC S9(04) SIGN LEADING SEPARATE` renders as
   `S9(04)`; only the SIZE (5 rather than 4) distinguishes it.
4. **`DEPENDING ON` never names its controlling item.** The listing renders
   `OCCURS 1 TO 4` and stops. That one fact is read from the copybook source by
   `gen_probe.find_odo_field`, and it is the *only* structural fact the harness
   takes from the source rather than from `cobc`.
5. **A GROUP row's SIZE covers all of its own occurrences; an ELEMENTARY row's
   SIZE covers one.** `D05-ROW` (group, OCCURS 3, 5 bytes each) reports SIZE
   `00015`; `D05-SLOT` (elementary, OCCURS 4, 5 bytes each) reports SIZE
   `00005`. This is asserted rather than trusted, and it is easy to get
   backwards.
6. **An item may not follow an ODO table in the same group** (§3.2).
7. **A variable-length group cannot be redefined** (§4.3).

None of these caused an oracle value to be adjusted. Where the compiler and the
standard as we read it differ, the compiler's measured behaviour is what the
oracle records.

## 9. What is sealed, and what is not

```
discovery-bench/
  SPEC.md                                     sealed
  seal.toml                                   sealed  (the include set, reviewable in a diff)
  corpus/*.cpy                                sealed  (15 files)
  harness/{__init__,gen_probe,oracle_layouts}.py
                                              sealed
  oracle/oracle.json                          sealed  (D7 — the answers, not just the inputs)
  results/                                    NOT sealed (mirrors bench/results)
  LEDGER_relian-discovery-bench-v0.1.json     the seal itself; written by the ceremony
tools/
  seal.py                                     NOT sealed — a tool, not a benchmark artifact
  verify_manifest.py                          NOT sealed — a verifier sealed inside what it
                                              verifies would be circular
```

**Consequence of sealing the oracle, stated so nobody is surprised:** a defect
in `gen_probe.py` after sealing requires **v0.2, a new seal and a new tag**.
Never a silent edit (ZCS-6 Phase 4).

`expected_absent` is empty and must stay empty. An entry appearing there means
the seal covers something the public repo cannot check, and that is an
escalation, not a declaration.

## 10. Reproducing this

```sh
# regenerate the oracle and diff it against the committed copy
RELIAN_REQUIRE_COBC=1 python3 -m discovery_bench.oracle_layouts --check     # via tests
python3 discovery-bench/harness/oracle_layouts.py --check                    # direct

# after the ceremony: verify the seal with no arguments beyond --ledger
python3 tools/verify_manifest.py \
    --ledger discovery-bench/LEDGER_relian-discovery-bench-v0.1.json \
    --from-manifest --pin-fingerprint 233bb4406e2de606
```

The fingerprint `233bb4406e2de606` is the published signer. "Any third party
can independently re-derive the ledger" is only true if the third party knows
which key to expect, so the fingerprint belongs in the customer-facing document
alongside the verification command, not only in the manifest that signs itself
(D13).
