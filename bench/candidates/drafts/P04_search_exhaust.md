# P04_taxtable held-out vector additions — SEARCH-exhaust window (sealing review draft)

**Status: DRAFT for Khaalis's v1.2 sealing review. Nothing here touches
`relian-bench-private`; authoritative vectors are regenerated by the private
generator at sealing. All numbers below were measured this session
(GnuCOBOL 3.1.2 oracle compiled from the public `program.cbl`; candidate =
the committed C1 `Taxtbl01.java`; jacoco-0.8.12).**

## Why

P04_taxtable measures 11/16 branches on BOTH splits. The Phase 1.5
line-level analysis located the two `_tx_search`-emitted branches — the
loop-exhaust branch (`for (; BI <= 5; BI++)`, Java line 85) and the AT END
fallback (`if (!_found)`, line 91) — as reachable but unexercised: no vector
on either split has an income above `BR-CEIL(5)` = 999999999.00, while
`WS-INC PIC 9(9)V99` admits up to 999999999.99. These additions close that
vector-coverage gap.

## The window

`SEARCH … AT END` fires exactly for incomes in **(999999999.00,
999999999.99]** — a 99-cent window at the top of the domain, independent of
filing status (row 5's ceiling is not multiplied by `WS-MULT`).

## Proposed vectors (oracle-measured expected outputs)

| input | expected stdout | expected_exit |
|---|---|---|
| `999999999.01,S` | `TAX=319977686.18 BRACKET=5 MARGINAL=0.3200` | 0 |
| `999999999.50,S` | `TAX=319977686.34 BRACKET=5 MARGINAL=0.3200` | 0 |
| `999999999.99,S` | `TAX=319977686.50 BRACKET=5 MARGINAL=0.3200` | 0 |
| `999999999.50,M` | `TAX=319955372.84 BRACKET=5 MARGINAL=0.3200` | 0 |
| `999999999.99,M` | `TAX=319955373.00 BRACKET=5 MARGINAL=0.3200` | 0 |

Optionally also `999999999.00,S` (`TAX=319977686.18 …`) as the last income
that still matches row 5 through the `WHEN` path — it pins the boundary from
below.

## Measured effect (public split + these five, candidate = committed Taxtbl01.java)

- BER **1.0 (17/17)** — the Java candidate matches the oracle on every
  added vector, so held-out is expected to stay green after sealing
  (expected, not measured: the private generator's actual values may differ
  within the window; any in-window value exercises the same branches).
- P04 branch coverage **11/16 → 13/16 (0.8125)**; line-level confirms 85 and
  91 fully covered. Remaining misses are runtime-helper branches only:
  line 13 (`R.dnumU` pad loop — structurally dead for a 1-digit operand) and
  line 19 ×2 (`R.rtrim` — needs an empty/blank filing status; a vector like
  `50000.00,` would cover one side if desired).
- If added to the public split too, public aggregate 55/68 → 57/68
  (0.8382); held-out aggregate would rise correspondingly (60/68 → 62/68 =
  0.9118 **expected**, to be measured by the first CI run after sealing).

## Two honesty notes for the review

1. **Output-indistinguishability at the boundary.** For `S`, incomes
   999999999.00 (WHEN path) and 999999999.01–.15 (AT END path) print the
   *same* TAX — the sub-cent difference disappears in the final `ROUNDED`
   (HALF_UP). These vectors therefore prove branch *exercise* (via JaCoCo)
   and behavioral agreement, but stdout alone cannot distinguish a candidate
   that skips the search and hard-codes bracket 5 as a fallback — the
   committed emission's `if (!_found) WS_IDX = 5` is behaviorally identical
   to a real AT END on this program. The `.50`/`.99` vectors DO
   discriminate tax amounts within the window, which is why they are
   included alongside `.01`.
2. **RETURN-CODE.** All rows expect exit 0; with WP-1.5.0d merged the
   scorer verifies that explicitly.
